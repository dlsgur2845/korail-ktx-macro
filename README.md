# KTX 잔여석 매크로 1.3.2

## 1.3.0 빈 결과의 원인과 예매 안내창 처리

### ‘해당 스케줄에 운행하는 열차가 없습니다’는 운행 없음이 아닙니다

코레일은 조회 결과 배열이 비어 있으면 무조건 이 문구를 띄웁니다. 그리고 조회 API가 실패하는 모든 경로에서 결과를 빈 배열로 초기화합니다. 즉 이 화면만으로는 통신 실패와 실제 빈 시간표를 구분할 수 없습니다.

조회 요청은 `dynaPath`가 서명한 1회용 주소(`POST /web_s/<토큰>/<임의경로>?fyb_=<난수>`)로 전송됩니다. 헤드리스 크롬으로 확인한 결과 같은 조회가 처음에는 HTTP 200으로 열차 10건을 반환했고, 이후 반복 조회에서는 계속 HTTP 500을 반환했으며 그때마다 이 빈 결과 화면이 떴습니다. 조회를 많이 보낼수록 실패가 늘어나는 세션 단위 제약으로 보입니다.

그래서 1.3.0은 이 상태를 `empty-result`로 이름을 바꿔 ‘조회 실패이거나 실제 운행 없음’으로 취급합니다. 2.5초 유지될 때만 재조회를 예약하고, 5초·10초·20초·40초·60초(상한)로 물러나며 최대 12번까지 시도합니다. 정상 목록을 받으면 실패 횟수를 초기화합니다.

### 예매 클릭 이후의 안내창을 처리합니다

이전 버전의 로딩만 돌고 예매 팝업이 안 뜨던 현상의 원인입니다. 코레일의 예매 버튼은 곧바로 예약을 보내지 않습니다. 비정차·연결편성 안내, 우회 안내, 지연승낙 안내, 단체 안내, 좌석 자동배정 확인, 좌석선택/열차예매 선택을 차례로 띄우고 사용자가 누를 때까지 기다립니다. 이전 버전은 예매를 누른 순간 상태를 `submitted`로 바꾸고 그 뒤로는 성공·실패 문구만 찾았으므로, 클릭 후에 뜬 안내창은 영원히 답을 받지 못했습니다.

이제 단계를 셋으로 나눕니다.

- `selecting` 좌석 선택 표시를 확인합니다. 선택 판정에 `title="선택"` 외에 좌석 칸의 `active` 클래스도 함께 봅니다.
- `confirming` 예매 버튼을 눌렀고 아직 예약 요청이 전송되지 않은 상태입니다. 알려진 안내창을 확인하며 요청 전송을 기다립니다.
- `submitted` `/web_r/` 예약 요청이 실제로 전송된 것을 확인한 상태입니다. 여기서는 어떤 버튼도 누르지 않습니다. 중복 예약을 막기 위한 기존 원칙을 유지합니다.

자동으로 확인하는 안내창은 승차권 내용을 바꾸지 않는 것만 기본값입니다.

| 안내창 | 기본값 | 이유 |
|---|---|---|
| 정차역·도착시간, 연결편성, 할인, 인접역 안내 | 자동 확인 | 내용 고지일 뿐 구입 조건이 바뀌지 않음 |
| 좌석선택 / 열차예매 선택 | 열차예매 선택 | 이 확장의 목적과 동일 |
| 지연 열차 승낙 | 꺼짐 | 지연배상을 받지 못함 |
| 우회 운행 승낙 | 꺼짐 | 도착시간이 달라짐 |
| 단체 위약금 안내 | 꺼짐 | 위약금 조건 고지 |
| 좌석 자동배정 동의 | 꺼짐 | 좌석을 임의 배정받음 |
| SRT 홈페이지 이동 | 항상 정지 | 다른 사이트로 나감 |
| 로그인 필요, 잔여석 없음, 처음 보는 안내 | 항상 정지 | 사람이 판단해야 함 |

꺼짐 항목은 추가 설정에서 직접 켜면 자동으로 확인합니다. 같은 안내창이 3번 반복되면 정지합니다.

### 그 밖의 수정

- 좌석 판정을 좌석 칸의 클래스(`price_box fl-l <상태>`)로 합니다. 코레일은 실제로 구입 가능할 때만 `gen`·`spe`·`yms` 토큰을 넣으므로, 열차 종류·언어에 따라 달라지는 한국어 라벨보다 안정적입니다. 기존 라벨 판정은 예비 경로로 남겼습니다.
- 입석+좌석을 켠 경우 하단 버튼이 `예매`가 아니라 `입석+좌석 예매`로 표시됩니다. 이전 버전은 이 버튼을 찾지 못해 시간 초과로 끝났습니다. 이제 두 라벨을 모두 인식하고 `예약대기신청`은 누르지 않습니다.
- 예약 성공 판정에 예약 상세 화면으로의 이동을 추가했습니다. 코레일은 성공 시 완료 문구 대신 상세 화면으로 라우팅합니다. 로그인 화면 이동은 세션 만료로 구분해 알립니다.
- `/web_r/` 요청이 전송되었는지를 기록하므로, 요청이 아예 나가지 않은 경우(대기열 차단, 미처리 안내창)와 전송 후 실패를 구분해 알립니다.
- **탭 재조회를 선택 항목으로 넣었습니다.** 기본값은 기존 새로고침입니다. 아래 별도 항목에 정리했습니다.
- **한 주기의 고정 지연을 줄였습니다.** 조회 간격 숫자보다 이쪽이 체감 속도를 지배합니다. 새로고침 한 번에서 조회 응답까지 걸리는 시간을 실측하니 약 1.0초였고(번들·런타임은 캐시에서 35ms·59ms, DOM 완료 458ms, 조회 요청 자체 372ms), 여기에 매크로가 얹던 고정 지연이 더 컸습니다.

  | 항목 | 이전 | 현재 |
  |---|---|---|
  | 목록 안정 대기 | 750ms | 300ms |
  | 조회 후 대기 기본값 | 1000ms | 0ms |
  | 화면 검사 주기 | 250ms | 120ms |
  | 한 주기 합계(추정) | 약 3.1초 | 약 1.5초 |

  조회 후 대기를 0으로 둘 수 있게 했습니다. 목록을 읽는 즉시 다시 새로고침하며, 실제 주기는 새로고침 시간이 결정합니다. 0에서도 거부가 관측되면 2초부터 백오프가 걸립니다.

- **조회 간격은 적응형입니다.** 기본 0초, 최소 0초입니다. 조회가 거부되면 단계가 1 올라 간격이 두 배가 되고, 조회가 정상이면 단계가 1 내려갑니다. 단계 상한은 4이므로 기준 3초에서 최대 48초이고, 절대 상한은 60초입니다. 현재 단계와 간격을 패널에 표시합니다.

  거부율에 따라 간격이 어디에 정착하는지 시뮬레이션한 값입니다.

  거부율에 따라 추가 대기가 정착하는 위치입니다. 기준 0초 기준이며 새로고침 시간은 별도입니다.

  | 거부율 | 추가 대기 |
  |---|---|
  | 0~10% | 없음 |
  | 30% | 2초 |
  | 50% | 4초 |
  | 80% 이상 | 16초 |

  완화 조건을 '정상 조회 3회 연속'으로 두는 방식을 먼저 시도했다가 버렸습니다. 거부율 30%에서는 3회 연속 성공이 거의 나오지 않아 간격이 상한까지 올라가고 감시가 무의미해졌습니다. 물러나는 목적은 부하를 줄이는 것이지 감시를 포기하는 것이 아닙니다.
- 대기 단계 시간 제한을 좌석 선택 25초, 요청 전송 40초, 결과 확인 45초로 늘렸습니다.
- **감시가 예상치 못하게 끝나면 알립니다.** 이전에는 재조회 한도 초과, 더보기 반복 실패, 접근 제한, 다른 탭과의 충돌, 새로고침 실패 같은 상황에서 패널 글자만 바뀌고 조용히 멈췄습니다. 탭을 최소화해두면 감시가 죽은 것을 모르고 기다리게 되는 가장 조용한 실패 경로였습니다. 이제 이런 정지 13곳이 모두 소리와 브라우저 알림을 냅니다. 좌석 발견과 구분되도록 알림 제목은 `KTX 매크로 정지`, 탭 제목은 `⚠️ KTX 매크로 정지`, 소리는 낮은음 2회입니다. 좌석 발견은 그대로 높은음 3회입니다. 사용자가 직접 누른 중지는 알리지 않습니다.

### 재조회 방식

이전에는 확인할 때마다 탭을 통째로 새로고침했습니다. 이제는 코레일 화면의 열차종별 탭에서 **이미 선택된 탭을 다시 누릅니다.** 이 버튼은 코레일의 검색 상태 설정 함수를 호출하고, 그 함수가 매번 새 객체를 만들기 때문에 값이 같아도 조회가 다시 실행됩니다. 즉 같은 조건으로 같은 결과를 다시 받아오며 사용자가 보는 필터는 바뀌지 않습니다.

실제 측정한 차이입니다.

| | 전체 새로고침 | 탭 재조회 |
|---|---|---|
| 코레일 API 요청 | 12건 | 10건 |
| 그중 실제 열차 조회 | 1건 | 1건 |
| 앱 부트스트랩 재실행 | 함 | 안 함 |
| `dynaPath` 런타임 244KB 재초기화 | 함 | 안 함 |
| 번들·CSS·폰트 재파싱, React 재마운트 | 함 | 안 함 |

**기본값은 새로고침입니다.** 탭 재조회로 바꾼 뒤 빈 결과가 절반 가까이 늘었다는 보고가 있어 선택 항목으로 내렸습니다. 원인은 확인하지 못했습니다. 의심하는 지점은 탭 클릭이 조회를 두 번 유발하고 늦게 끝난 쪽이 실패하면서 목록을 비우는 경우입니다. 코레일의 조회 실패 처리가 결과 목록을 빈 배열로 만들기 때문에, 성공한 조회가 있어도 화면이 비게 됩니다. 확인 전까지는 쓰지 마세요.

API 요청 수 자체는 12건에서 10건으로 조금 줄어드는 정도입니다. 실질적인 이득은 앱 전체를 다시 세우지 않는다는 점이고, 그래서 확인 한 번이 훨씬 빨리 끝납니다. 패널도 다시 그려지지 않습니다.

조회 요청의 HTTP 상태는 재조회 방식과 무관하게 항상 읽습니다. 패널 상태 문구 마지막 줄에 `마지막 조회 응답: HTTP 500`처럼 표시되고, 진행 기록에도 `query-response`로 남습니다. 빈 결과 화면을 보고 추측하지 않고 실제 응답으로 판단할 수 있습니다.

브라우저가 응답 상태를 제공하지 않으면(크롬 109 미만) 이 줄은 표시되지 않습니다.

안전장치를 뒀습니다. 활성 탭 버튼을 찾지 못하면 기존 새로고침으로 대체합니다. 클릭 후 15초 동안 조회 응답이 없으면 새로고침으로 대체합니다. 오류 복구는 그대로 전체 새로고침을 씁니다. 상태가 깨졌을 때는 더 강한 초기화가 낫기 때문입니다. 재조회로 목록이 새로 오면 더보기 묶음 추적을 1번부터 다시 셉니다.

### 빈 결과의 실제 주된 원인 (사용자 진단 기록으로 확인)

진행 기록을 받아 원인을 특정했습니다. 빈 결과 화면의 상당 부분은 코레일의 속도 제한이 아니라 **이 매크로가 누르는 더보기** 때문이었습니다.

받은 기록의 순서입니다.

```
09.633  query-response  HTTP 200     ← 첫 조회 성공
09.997  more-request    rows 10      ← 열차 10건이 떠 있는 상태에서 더보기 클릭
10.001  more-call / more-event
10.590  query-response  HTTP 500     ← 더보기 조회가 거부됨
13.114  more-failure
13.115  query-recovery-scheduled     ← 빈 결과로 판정, 5초 복구 대기
```

첫 조회가 200으로 열차 10건을 정상 수신했는데, 그 뒤 더보기 조회가 500을 받자 화면이 비었습니다. 코레일은 조회 실패 시 결과 목록을 빈 배열로 만들기 때문에, **더보기 실패가 이미 받아둔 첫 묶음까지 지웁니다.** 이전 버전은 이것을 '운행 열차 없음'으로 보고 복구 새로고침을 예약했습니다.

특정 열차 기준에서 선택한 열차가 첫 목록에 없으면 매크로는 매 주기마다 더보기를 누릅니다. 그래서 주기당 조회가 1건이 아니라 최대 3건이 되고, 그중 하나만 실패해도 화면이 빕니다. 참고로 매크로 없이 페이지를 한 번 로드하면 조회는 정확히 1건만 나갑니다. 즉 사이트가 중복 조회를 보내는 것이 아닙니다.

수정한 내용입니다.

- 더보기 실패를 빈 결과로 판정하지 않습니다. 첫 조회는 정상이었으므로 거부로 세지 않고, 지수 대기 없이 곧바로 다시 조회합니다.
- 같은 범위에서 더보기가 2번 실패하면 더보기를 중단하고 첫 목록만 감시합니다. 패널에 `더보기 중단됨 · 첫 목록만 감시 중`으로 표시합니다.
- 더보기가 중단된 상태에서 특정 열차 기준이고 선택한 열차를 첫 목록에서 본 적이 없으면, 감시가 무의미하므로 알림과 함께 정지합니다.

**가장 효과적인 대응은 웹에서 조회 시작 시각을 감시할 열차 출발 시각 근처로 맞추는 것입니다.** 그러면 선택한 열차가 첫 목록에 들어와 더보기가 아예 필요 없어지고, 주기당 조회가 1건으로 줄어 이 실패 경로가 사라집니다. 받은 기록의 목록 범위는 05:39~13:18이었는데, 감시 대상 열차가 그보다 뒤에 있었습니다.

### 1.3.1 수서 열차, 강조 표시, 알림

- **특정 열차 기준에서 도착역을 확인하지 않습니다.** `서울·용산 - 수서 함께 보기`나 `인접역 보기`를 켜면 코레일은 검색란과 출발·도착역이 다른 열차도 목록에 넣습니다. 이전 버전은 검색란과 정확히 일치해야만 매칭했으므로, 밀양→서울로 조회한 목록에서 수서행 열차를 골라도 영원히 찾지 못했습니다. 그리고 특정 열차 기준에서는 대상을 못 찾으면 매 주기마다 더보기를 누르므로, 그 더보기 실패가 빈 결과 화면으로 나타났습니다. 이전 스크린샷의 오류가 이것입니다. 열차 번호는 그 목록에서 고른 것이니 열차 자체가 사용자의 선택입니다. 이제 KTX 종별과 번호만 확인합니다.
- **시간대 기준은 그대로 엄격합니다.** 시간대 기준은 열차가 아니라 구간과 시간으로 고르는 방식이라, 도착역을 확인하지 않으면 조회한 곳과 다른 목적지를 예매할 수 있습니다. 수서행을 감시하려면 특정 열차 기준을 쓰세요.
- **이전 실행의 파란 강조 표시를 지웁니다.** 강조를 지우는 코드가 아예 없어서, 102를 감시해 찾은 뒤 204를 감시하면 두 줄 모두 강조가 남았습니다. 시작할 때와 새로 찾을 때 기존 강조를 지웁니다.
- **알림이 나가지 못하면 그 사실을 표시합니다.** 알림음용 오디오 컨텍스트는 시작 버튼을 누른 탭에서만 만들어졌는데, 매크로는 재조회를 위해 탭을 새로고침하므로 좌석을 찾은 시점에는 사라진 상태였습니다. 이제 필요할 때 다시 만들고, 브라우저가 소리를 차단했거나 확장 연결이 끊겨 브라우저 알림을 보내지 못한 경우 패널에 `⚠`와 함께 사유를 적습니다. 조용히 실패하지 않게 했습니다. 다만 새로고침 직후에는 사용자 조작 기록이 없어 브라우저가 소리를 막을 수 있습니다. 확실한 채널은 브라우저 알림이므로 운영체제 알림 권한을 확인해주세요.

### 1.3.2 감시 대상 열차 표시

감시 중인 열차를 웹 목록에서 바로 알 수 있게 표시합니다.

| 표시 | 의미 |
|---|---|
| 회색 점선 테두리 | 이 열차를 감시하고 있음 |
| 파란 실선 링 | 좌석을 발견한 열차 |

두 표시는 CSS 속성이 달라서(점선은 `outline`, 발견은 `box-shadow`) 겹쳐도 서로를 지우지 않습니다. 마우스를 올리면 감시 중이라는 설명이 나옵니다. 코레일이 재조회할 때마다 열차 줄을 다시 그리므로 매 검사마다 표시를 다시 입힙니다. 중지하면 감시 표시를 지우고, 발견 표시는 어느 열차였는지 확인할 수 있도록 남깁니다.

특정 열차 기준에서는 선택한 번호의 열차에, 시간대 기준에서는 지정한 시간대에 드는 열차에 표시됩니다. 판정은 좌석을 찾을 때와 똑같은 기준을 쓰므로, 표시가 안 되면 그 열차는 감시되지 않는 것입니다. 설정이 의도대로 걸렸는지 눈으로 확인할 수 있습니다.

패널에도 `10개 열차 확인 (05:39~13:18) · 감시 대상 1개`처럼 현재 목록에서 몇 개가 감시 대상인지 표시합니다.

### 남은 한계

완벽한 예매를 보장하지 않습니다. 다음은 이 확장이 해결할 수 없습니다.

- 대기열이 `Block` 판정을 내리면 코레일 코드가 다음 단계 콜백을 호출하지 않고 끝냅니다. 오류도 남지 않습니다. 이제 이 상황을 시간 초과 대신 ‘요청이 전송되지 않음’으로 구분해 알리지만, 통과시킬 방법은 없습니다.
- 반복 조회로 서명 요청이 거부되면(HTTP 500) 물러나서 다시 시도하는 것 외에 할 수 있는 일이 없습니다. **탭 재조회로 바꿔도 이 문제는 그대로입니다.** 거부되는 대상이 열차 조회 요청 자체이고, 그 요청은 어느 방식이든 1건씩 나갑니다. 실제로 이미 막힌 세션에서 탭 재조회를 시험했더니 똑같이 500이 왔습니다. 재조회 방식 변경은 부하와 속도를 개선하는 것이고 차단을 피하는 수단이 아닙니다.
- 실제로 좌석이 없는 경우, 로그인 세션 만료, 켜지 않은 안내창.

요청 서명 재현, 신뢰된 입력 위장, 지문·간격 조작으로 매크로 탐지를 피하는 기능은 넣지 않았습니다. 가장 확실한 방법은 ‘알림 후 정지’로 두고 알림이 오면 예매 버튼만 직접 누르는 것입니다.

## 1.1.14 브라우저 새로고침

일반 재조회와 오류 복구 시 페이지 스크립트의 `location.reload()` 대신, 백그라운드 서비스 워커가 `chrome.tabs.reload(발신 탭 ID, {bypassCache:false})`로 브라우저에 일반 새로고침을 요청합니다. 실제 F5 키를 입력하는 방식은 아닙니다. 캐시를 강제로 무시하지 않습니다. 추가 권한은 없습니다. [Chrome Tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs#method-reload)

실행 중인 코레일 조회 탭만 대상으로 합니다. 메시지가 지정한 임의 탭이나 현재 활성 탭을 선택하지 않습니다. 새로고침을 요청한 뒤에는 중복 요청하지 않으며, 실패 응답이나 10초 동안 페이지가 이동하지 않는 경우 정지합니다. 페이지 이동으로 메시지 연결이 끊어질 수 있으므로 연결 종료만으로 실행 상태를 지우지 않습니다.

업데이트 시 **매크로 중지 → 설치 폴더 파일 교체 → chrome://extensions의 확장 프로그램 새로고침 → 코레일 탭 새로고침**을 모두 해주세요. 백그라운드 코드도 바뀌었으므로 코레일 탭만 새로고침하면 적용되지 않을 수 있습니다.

모의 테스트 60개 통과. 더보기 실패와 자동 예매 HTTP 500의 해결 여부는 실제 사이트에서 추가 확인이 필요합니다. 이번 변경은 새로고침 실행 방식을 바꾼 것입니다.

코레일 일반 예매 웹의 KTX 잔여석을 확인하고 **좌석 선택 → 안내창 확인 → 하단 예매 클릭 → 예약 요청 전송 확인**까지 진행하는 크롬·엣지 확장 프로그램입니다. 결제는 자동으로 하지 않습니다. 명절 전용 사이트는 지원하지 않습니다.

## 설치·업데이트

1. ZIP을 압축 해제합니다.
2. 크롬 `chrome://extensions` 또는 엣지 `edge://extensions`에서 개발자 모드를 켭니다.
3. ‘압축해제된 확장 프로그램을 로드합니다’로 `manifest.json`이 있는 폴더를 선택합니다.
4. 코레일 탭을 새로고침합니다.

업데이트는 기존 폴더의 파일 교체 → 확장 프로그램 관리 화면에서 새로고침 → 코레일 탭 새로고침 순서입니다. 이전 ‘좌석 선택 후 정지’ 설정은 ‘좌석 선택 후 예매 요청’으로 전환하고 실행을 중지합니다. 설정을 확인한 뒤 다시 시작하세요. 이전에 ‘알림 후 정지’를 사용했다면 자동으로 예매 모드로 바꾸지 않으므로 직접 변경해주세요.

## 사용

1. 코레일에 **미리 로그인**하고 편도의 구간·날짜·인원·조회 시작 시각을 직접 지정하여 조회합니다.
2. 감시 기준을 선택합니다. **특정 열차 기준**은 한 개 이상의 열차 번호만 적용하며 시간대는 무시합니다. **시간대 기준**은 지정 시간대의 KTX를 검사하며 저장된 열차 번호는 무시합니다. 적용하지 않는 조건 입력란은 숨깁니다.
3. 특정 열차 기준에서는 ‘목록에서 선택’을 누르거나 번호를 `027, 213, 263`처럼 입력합니다. 시간대 기준에서는 출발 시간 범위를 입력합니다. 일반실/특실도 지정하세요. 시간 범위는 웹 검색 결과를 거르는 조건이며 웹의 조회 시각을 바꾸지 않습니다.
4. 입석+좌석을 원하면 ‘입석+좌석도 포함’을 켭니다. 일반실 또는 일반실 우선 설정에서만 적용되며 순수 입석은 포함하지 않습니다.
5. **‘좌석 발견 시’를 ‘좌석 선택 후 예매 요청’으로 설정**하고 시작합니다.
6. 예매 결과 알림 후 예약 내역과 결제 기한을 확인하고 직접 결제합니다.

목록에 없는 열차는 웹의 더보기를 누르고 선택 목록을 다시 불러오세요. 기존에 선택한 번호는 유지됩니다. 날짜·구간·인원 변경 시 실행은 정지합니다. 두 모드 모두 검색 날짜·구간과 좌석 등급은 유지됩니다. 특정 열차 기준에는 시간 조건을 적용하지 않습니다. 인접역 열차는 출발/도착역이 검색 구간과 다르면 제외됩니다.

## 조회 범위와 속도

조회 범위와 실행 시간 입력란은 제거했습니다. 특정 열차 기준은 최초 목록과 더보기 최대 2번(총 3묶음)을 검사하며 선택 열차를 모두 찾으면 일찍 끝냅니다. 시간대 기준은 시간순 목록을 더보기로 불러와 종료 시각보다 늦은 열차가 나타나거나 더보기가 없어질 때까지 검사합니다. 원하는 시간이 뒤쪽에 있으면 2회를 넘겨서도 진행합니다. 웹 조회 시작 시각보다 앞선 열차는 더보기로 불러올 수 없으므로 웹에서도 적절한 시작 시각을 지정해주세요.

화면을 0.25초마다 로컬에서 검사합니다. 목록이 0.75초 이상 안정되고 표시된 로딩이 끝나면 검사하고, 조건에 맞는 좌석이 없으면 설정한 간격(기본 3초, 최소 2초) 후 새로고침합니다. 실행 시간 제한은 없습니다.

헤드리스 크롬으로 시험할 때는 조회를 15~20회쯤 보낸 뒤부터 세션 전체가 HTTP 500을 반환했고, 다른 날짜·구간으로 새로 접속해도 계속 실패했습니다. 처음에는 이를 조회 속도 제한으로 해석했습니다.

그런데 실제 크롬에서 1초 간격으로 직접 새로고침하면 대기열 화면이 뜨는 경우를 제외하고 문제가 없다는 보고가 있습니다. 그렇다면 위 500은 속도 때문이 아니라 자동화 도구가 감지된 결과일 수 있습니다. `dynaPath` 런타임이 `navigator.webdriver`, 플러그인 수, 플랫폼, WebGL 정보를 읽는 것은 확인했습니다. 즉 그 측정은 속도 제한의 근거로 쓰기에 신뢰할 수 없습니다.

그래서 안전한 상수를 정해두는 대신 사용자가 지정한 속도로 돌리고, 실제 거부가 관측될 때만 물러나게 했습니다. 최소 간격 제한도 1초로 되돌렸습니다.

정확한 임계값은 측정하지 못했습니다. 기본 3초는 관측에 근거한 판단값이며 최적값이라는 뜻은 아닙니다. 더 짧게 쓰고 싶으면 2초까지 내릴 수 있고, 거부가 시작되면 자동으로 물러납니다. 예매 성공 확인 시 정지하고, 예매 결과 불명확·접근 제한·반복 오류 등 직접 확인이 필요한 상황에서도 정지합니다. 이는 네트워크 요청 자체가 아니라 DOM 상태 기반의 완료 판단입니다.

조회 오류 또는 빈 결과, 목록·로딩·더보기의 60초 시간 초과에서는 5초부터 두 배씩 늘려 60초를 상한으로 최대 12번 재조회합니다. 정상 목록을 확인하면 오류 횟수를 초기화합니다. 대기열은 기다리고 접근 제한은 정지합니다. 다른 오류 문구나 브라우저 기본 alert 창은 감지하지 못할 수 있습니다.

- 조건에 맞는 좌석을 발견하면 즉시 조회 새로고침을 중단하고 해당 좌석 링크를 선택합니다.
- 승차권 내용을 바꾸지 않는 안내창(정차역·연결편성·할인·인접역)은 자동으로 확인합니다. 구입 조건이 달라지는 안내창은 추가 설정에서 켠 경우에만 확인하고, 그 밖의 안내는 정지합니다. 위 1.3.0 표를 참고하세요.
- 해당 열차의 좌석이 선택된 표시를 확인하고, ‘열차시각·운임요금·좌석선택’이 있는 하단 영역의 ‘예매’를 한 번 누릅니다. 상단의 동명 메뉴는 누르지 않습니다.
- 요청 상태를 먼저 저장하므로 요청 이후 페이지 이동/새로고침으로 중복 요청하지 않습니다.
- 예매 완료 문구 또는 예약 상세 화면 이동이 확인되면 알립니다. 그 밖의 페이지 이동은 성공으로 단정하지 않고, 로그인 페이지 이동은 세션 만료로 구분해 알립니다.
- 좌석 선택 25초, 요청 전송 40초, 결과 확인 45초가 지나도 확인되지 않으면 정지합니다. 예매 실패 및 알 수 없는 결과에서는 자동 재요청하지 않습니다. 예약 내역을 확인하고 다시 시작하세요.

‘알림 후 정지’ 모드는 좌석 발견 시 알리기만 합니다. 예매 모드에서도 계정 상태·안내창·서버 응답에 따라 실제 예약에 실패할 수 있습니다.

## 패널과 알림

조회 설정의 펼침/접힘 상태는 같은 탭의 새로고침 후에도 유지됩니다. 패널은 창 높이에 맞춰 내부 스크롤을 지원하고 시작·중지 버튼은 하단에 고정됩니다. 브라우저 알림이 운영체제에서 허용되어 있어야 알림을 받을 수 있습니다.

알림은 두 가지입니다. 좌석 발견 또는 예매 결과는 `KTX 잔여석 발견`으로 높은음 3회, 감시가 예상치 못하게 끝나면 `KTX 매크로 정지`로 낮은음 2회입니다. 어느 쪽이든 알림을 클릭하면 해당 코레일 탭이 앞으로 옵니다. 소리는 시작 버튼을 누를 때 열린 오디오 컨텍스트를 사용하므로, 시작하지 않은 상태에서는 소리가 나지 않습니다.

탭을 닫거나 컴퓨터가 잠들면 실행이 중단될 수 있습니다. 브라우저 절전 모드로 타이머가 지연될 수 있습니다. 로그인 정보는 읽거나 저장하지 않고 검색 조건·실행 상태를 탭의 세션 저장소에 저장합니다. 같은 도메인에서 중복 실행을 방지하며 www 유무가 다른 두 도메인은 동시에 실행하지 마세요.

## 1.1.13 빈 결과 복구와 시간대 더보기

- ‘해당 스케줄에 운행하는 열차가 없습니다’ 안내가 1.5초 유지될 때만 복구를 예약합니다. 로딩 중에는 기존 복구 시간이 지났어도 즉시 새로고침하지 않습니다. 정상 목록이 나타나면 복구 예약을 취소합니다.
- 날짜·구간·인원이 지정되어 있으면 운행 없음/조회 오류 화면에서도 시작하여 복구할 수 있습니다. 사용자가 중지한 경우에는 다시 시작하기 전까지 동작하지 않습니다.
- 시간대 모드는 종료 시각을 포함하는 모든 열차를 확인하기 위해, 종료 시각보다 늦은 출발 열차가 나올 때까지 더보기합니다. 예: 14:00~18:00이면 18:00이 마지막인 목록에서도 한 번 더 조회합니다. 더보기가 없으면 확장을 끝냅니다.
- 더보기 결과는 열차 개수만이 아니라 열차 번호와 구간·시각의 변화로 확인합니다. 버튼/링크 형식을 모두 인식하고 결과를 기다리는 동안 중복 클릭하지 않습니다.
- 현재 확인한 출발 시각 범위를 패널에 표시하며, more-request / more-call / more-event / more-result / more-failure와 복구 예약을 진단 기록에 남깁니다.
- 같은 구간의 더보기가 실패한 기록은 첫 목록이 정상 복구돼도 유지합니다. 3초·6초·12초 복구 후 다시 실패하면 전체 시간대를 확인하지 못했다고 알리고 정지합니다. 원하는 범위 전체를 조회한 뒤 실패 기록을 초기화합니다.
